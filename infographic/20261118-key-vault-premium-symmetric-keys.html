Key Vault Premium で対称キー
(oct-HSM / AES) サポートが GA

Microsoft Ignite に合わせて発表 — FIPS 140-3 Level 3 の HSM 保護された AES キーを、マルチテナントの Key Vault Premium で本番利用可能に

📋概要

2026 年 7 月のパブリックプレビューを経て、Azure Key Vault Premium における対称キー (oct-HSM キータイプ) のサポートが一般提供 (GA) されました。AES (Advanced Encryption Standard) アルゴリズムを使用したデータの暗号化・復号・キーラップ・アンラップを Key Vault Premium 上で直接実行できます。

対称キーは HSM 保護のみ (oct-HSM) で提供され、Premium SKU の Vault が必要です。新規に作成されるキーは最新の HSM Platform 2 (FIPS 140-3 Level 3 検証済み HSM) で保護されます。また、256 ビットキーで使用する AES アルゴリズムは CNSA 2.0 (Commercial National Security Algorithm Suite 2.0) の要件に照らして耐量子 (quantum-resistant) とされており、ポスト量子暗号 (PQC) への備えとなるシナリオにも有効です。

GA に伴い、本番ワークロードに求められるパフォーマンス・スケーラビリティ・信頼性が提供され、Azure が管理するセキュリティ・コンプライアンス・運用管理の恩恵を受けながら対称キーを利用できます。

❌ Before (アップデート前の課題)

  • Key Vault (Vaults) がサポートするキータイプは RSA と EC (非対称キー) のみで、対称キーを扱うには単一テナントの Managed HSM (高コスト) や外部のキー管理基盤が必要だった
  • AES による暗号化・キーラップを HSM 保護で行いたい場合、マルチテナントで低コストな Vault では実現できなかった

✅ After (アップデート後の改善)

  • Key Vault Premium の oct-HSM キータイプで、HSM 保護された対称キー (AES 128/192/256 ビット) を作成・利用可能に
  • encrypt / decrypt / wrapKey / unwrapKey を AES-KW、AES-GCM、AES-CBC で実行でき、HMAC (HS256/HS384/HS512) による署名・検証にも対応
  • 本番ワークロードでの利用がサポートされ、既存の Azure セキュリティワークフローと統合して一元的にキーを管理

⭐主要機能

🔑

1. HSM 保護された対称キー (oct-HSM)

Key Vault Premium で 128 / 192 / 256 ビットの AES 対称キーを作成可能。対称キーは HSM 保護のみで、ソフトウェア保護版は提供されない。

🔒

2. AES による暗号操作

encrypt / decrypt / wrapKey / unwrapKey 操作に対応。アルゴリズムは AES-KW (キーラップ、RFC 3394)、AES-GCM (NIST SP 800-38d)、AES-CBC (NIST SP 800-38a) をサポート。

✍️

3. HMAC による署名・検証

oct-HSM キーで HS256 / HS384 / HS512 (HMAC-SHA) の Sign / Verify 操作に対応。

🛡️

4. 耐量子性 (CNSA 2.0 準拠)

256 ビットキーで使用する AES アルゴリズムは CNSA 2.0 の FAQ において耐量子とされ、ポスト量子暗号への移行準備に活用できる。

🚀

5. 本番ワークロード対応 (GA)

2026 年 7 月のパブリックプレビューから GA に昇格し、本番環境で必要なパフォーマンス・スケーラビリティ・信頼性を提供。

🛠️設定方法

前提条件

  • Premium SKU の Key Vault (対称キーは HSM 保護のみのため Standard では利用不可)
  • キー操作の権限 (Azure RBAC の場合: Key Vault Crypto Officer / Key Vault Crypto User など)

Azure CLI

bash対称キーの作成と AES-GCM 暗号化
# AES 256 ビット対称キーの作成 (oct-HSM)
az keyvault key create \
    --vault-name <vault-name> \
    --name sample-aes-key \
    --kty oct-HSM \
    --size 256 \
    --ops encrypt decrypt wrapKey unwrapKey

# AES-GCM によるデータの暗号化 (値は Base64 エンコード)
az keyvault key encrypt \
    --vault-name <vault-name> \
    --name sample-aes-key \
    --algorithm A256GCM \
    --value aGVsbG8gd29ybGQ= \
    --query "{iv:iv, result:result, tag:tag}"
注意: AES-GCM 操作では、暗号化レスポンスの iv、result、tag の 3 つの値を保存する必要があります。復号にはこの 3 つすべてが必要です。

💡メリット

💼 ビジネス面

  • Managed HSM (単一テナント・高コスト) を導入せずに、マルチテナントで低コストな Key Vault Premium で HSM 保護の対称キーを利用でき、コンプライアンス要件 (FIPS 140-3 Level 3) を満たしやすい
  • 256 ビット AES の耐量子性 (CNSA 2.0) により、ポスト量子暗号への移行を見据えたセキュリティ戦略を前倒しで実行できる
  • キー管理を Azure に集約することで、セキュリティ・コンプライアンス・運用の管理負荷を軽減できる

🔧 技術面

  • AES-GCM / AES-CBC による暗号化・復号、AES-KW によるキーラップを Key Vault の REST API / CLI / SDK から直接実行できる
  • キー素材は HSM 外に出ず、エクスポート不可のため、キーの漏えいリスクを最小化できる
  • key_ops プロパティによるキー単位の操作制限や、Azure RBAC によるきめ細かなアクセス制御が可能

🚧デメリット・制約事項

  • 対称キーは Key Vault Premium のみの提供。Standard SKU では利用できない
  • 暗号操作の入力サイズは 4,096 バイト (Base64 エンコード前) が上限のため、大きなデータの直接暗号化には不向き。大容量データはエンベロープ暗号化 (DEK を wrapKey で保護) が前提となる
  • 対称キーのキー素材は Get 操作で取得できない (HSM 保護のみ)。ローカルでの暗号処理が必要な場合は設計の見直しが必要
  • AES-GCM では iv・result・tag の 3 値の管理が必要で、いずれかを失うと復号できない

🎯ユースケース

📦 ユースケース 1: エンベロープ暗号化における KEK (キー暗号化キー) の HSM 保護

シナリオアプリケーションがローカルで生成したデータ暗号化キー (DEK) を、Key Vault Premium の oct-HSM キーを KEK として AES-KW でラップし、暗号化済み DEK をデータと共に保存する。

bashKEK の作成例
# KEK として AES 256 ビット対称キーを作成
az keyvault key create \
    --vault-name my-premium-vault \
    --name envelope-kek \
    --kty oct-HSM \
    --size 256 \
    --ops wrapKey unwrapKey

効果DEK は常に HSM 保護された KEK でラップされた状態で保存され、KEK 自体は Vault から出ないため、大容量データの暗号化と高いキー保護レベルを両立できる。

⚛️ ユースケース 2: ポスト量子暗号 (PQC) への準備

シナリオ規制の厳しい業界 (金融・公共など) で、CNSA 2.0 への準拠を見据え、暗号基盤を耐量子アルゴリズムへ移行する。

効果256 ビット AES は CNSA 2.0 において耐量子とされており、RSA ベースのキーラップから oct-HSM (AES-KW) へ移行することで、量子コンピュータ時代に向けた暗号アジリティを確保できる。

🔗関連サービス・機能

Azure Key Vault Managed HSM

単一テナントの HSM プール。oct-HSM 対称キーを従来からサポートしており、より厳格なセキュリティ・コンプライアンス要件を持つ高価値キー向け。今回の GA により、マルチテナントの Key Vault Premium でも対称キーが利用可能になった。

Azure RBAC

キーへのアクセス制御の推奨モデル。Key Vault Crypto Officer / Crypto User / Service Encryption User の組み込みロールでキー操作を管理。

カスタマーマネージドキー (CMK)

Azure Storage や Azure SQL などのサーバー側暗号化で Key Vault のキーを利用する構成。Key Vault を軸としたキー管理の代表的なシナリオ。

Azure Storage クライアント側暗号化

Key Vault のキーを使ったクライアント側データ暗号化のシナリオで、対称キーのラップ操作と組み合わせて利用可能。

Azure Key Vault Premium での対称キー (oct-HSM / AES) サポートが GA となり、Managed HSM を導入せずに FIPS 140-3 Level 3 の HSM 保護された AES キーを本番ワークロードで利用できるようになりました。AES-KW / AES-GCM / AES-CBC による暗号操作と HMAC 署名に対応し、256 ビットキーは CNSA 2.0 で耐量子とされるため、PQC 移行の布石としても有効です。

現在 Managed HSM や外部 KMS で対称キーを管理しているワークロードについては、要件 (テナント分離・コンプライアンスレベル) を確認のうえ、Key Vault Premium への集約によるコスト最適化を検討することを推奨します。なお、暗号操作の入力上限は 4,096 バイトのため、大容量データはエンベロープ暗号化パターンで設計してください。
