Microsoft Ignite に合わせて、エージェントの「ガバナンス」「ナレッジ接続」「業務データ連携」を支える 3 機能が一般提供に
📅 リリース日: 2026-11-17 🛠️ 対象: hosted agents / Foundry IQ / Work IQ

📋概要: 3 つの GA アップデート

1

🛡️ Hosted agents のネットワーク Egress 制御 (GA)

Hosted agent のアウトバウンド接続を順序付きルールで制御。宛先ホスト (FQDN、*.contoso.com のワイルドカード対応) でマッチし、Allow / Deny / Rewrite / ヘッダー変更を適用。ルールは RAI ポリシーに属し、サンドボックスの外側で強制される。

⏱️ 2026 年 7 月プレビュー → 11 月 GA
2

🔌 Foundry IQ の MCP サーバーナレッジソース (GA)

MCP サーバーを読み取り専用のフェデレーテッドナレッジソースとして登録。Web 検索や AI Search ベクトルインデックスに同期された Blob の非構造化データなど、他ソースと並んでクロスソース選択に参加する。

⏱️ 2026 年 6 月プレビュー → 11 月 GA
3

💼 Work IQ の Business Applications サポート (GA)

ビジネス接続型エージェントをより速く構築可能に。カスタム統合作業を削減し、エンタープライズデータを実用的なワークフローに変換。顧客のアクセス許可設定と環境制御は維持される。

⏱️ 7 月プライベート PV → 9 月パブリック PV → 11 月 GA

❌ Before (アップデート前の課題)

  • Hosted agent のアウトバウンド通信制限はプレビュー段階で、本番環境での外部接続先の統制が困難。エージェント自身のコードに依存しない通信制御が求められていた
  • Foundry IQ のナレッジソースはインデックス型 (AI Search、Blob、Azure SQL など) が中心で、インデックス化できないライブデータの利用にはカスタム統合が必要
  • ビジネスアプリのデータ接続には個別のカスタム統合作業が必要で、開発に時間がかかっていた

✅ After (アップデート後の改善)

  • 順序付きルール (先勝ち評価、既定 Deny/Allow、フェイルクローズ) で外部接続を本番品質で統制。Audit モードで影響確認 → Enforce へ移行可能
  • MCP サーバーを登録するだけで、インジェストパイプラインなしにクエリ時のライブデータ取得と統合ランキングでのマージが可能
  • 権限制御を維持したまま、既存ビジネスアプリのデータをエージェントのワークフローに組み込み可能

🔍サービスアップデートの詳細

1. Hosted agents のネットワーク Egress 制御 (GA)

Microsoft Learn ドキュメントで確認できた仕様は以下のとおりです。

ルール評価の仕組み

🥇

先勝ち評価 (first match wins)

ルールは上から順に評価され、最初にマッチしたルールが適用される。どのルールにもマッチしない場合は既定アクションを適用 — 許可リスト運用なら既定 Deny (推奨)、拒否リスト運用なら既定 Allow。

⚙️

プラットフォーム基盤ドメインは自動許可

Egress ポリシー適用時、エージェントランタイムの動作に必要な基盤ドメインは自動的に許可されるため、既定 Deny でもプラットフォーム接続用のルール追加は不要。

🎯

ホスト + パスでマッチ、4 種のアクション

各ルールはリクエストホストでマッチし、パスマッチも指定可能。*.contoso.com のようなホストワイルドカードをサポート。アクションは Allow / Deny / Transform (プレビュー: リクエストを許可しヘッダーを変更) / Rewrite (別の宛先にリダイレクト)。

🔒

フェイルクローズ評価・ルール上限

ポリシーを評価できない場合、リクエストは拒否される (フェイルクローズ)。ルール数の上限は 1 ポリシーあたり 480 ルール (上限引き上げはサポートリクエストで申請可能)。

強制モード

モード動作使いどころ
Auditトラフィックは通常どおり流れ、拒否対象のリクエストはブロックせずログに記録強制前にエージェントの接続先を観察
Enforceマッチしたルールを適用し、拒否対象のリクエストをブロックAudit モードで検証後の本番強制
⚠️ 注意: Audit モードが変えるのは Deny アクションの挙動のみ。Transform と Rewrite は Audit モードでも適用されます。

その他の仕様

  • ルールはエージェントにアタッチする RAI ポリシー (Microsoft.CognitiveServices/accounts/raiPolicies) の egressPolicy プロパティに格納され、安定版 2026-09-01 API バージョンで構成する
  • ルールが拒否した場合、Egress プロキシはエージェントのネットワーククライアントに HTTP 403 を返す
  • HTTPS トラフィックの検査のため、ランタイムは Egress プロキシの CA をサンドボックスの信頼バンドルに注入する (CA は約 30 日でローテーションされるため、ピン留め・永続化は不可)
  • Egress 判定はプロジェクトの Application Insights とトレースモニタリングに送信され、Foundry ポータルのプレイグラウンド (「Network egress decision」スパン) や Application Insights のログで確認できる

2. Foundry IQ の MCP サーバーナレッジソース (GA)

📡

「リモート」ナレッジソース — クエリ時のライブ取得

MCP サーバーを読み取り専用のナレッジソースとして Foundry IQ に登録できる。コンテンツは Foundry IQ にインジェストされず、クエリ時に MCP サーバーのツールを呼び出してライブデータを取得する。

🧠

LLM によるツール選択とランク付け

クエリ時にはナレッジベースに構成された LLM がツールを選択し、呼び出し引数を生成。Foundry IQ がツールを呼び出し、結果をランク付けされた参照として返す。

🔀

クロスソース選択・統合ランキング

他のナレッジソース (Web 検索、Azure AI Search ベクトルインデックスに同期した Blob の非構造化データなど) と並んでクロスソース選択に参加し、取得結果は統合ランキングパイプラインでスコアリング・マージ・リランクされる。

🔑

柔軟な認証・出力処理オプション

認証: foundryConnection (Foundry Agent Service からの呼び出し時に資格情報を注入)、storedHeaders (静的 API キーなど)、クエリ時のヘッダーパススルー (リクエスト単位の資格情報)。ツールごとに出力パース (auto / json / split / none) とリランク処理 (rerank / none) を構成可能。

⚠️ 注意: Azure Updates では GA と発表されていますが、執筆時点の Microsoft Learn ドキュメント (2026-11-09 版) では MCP Server knowledge source はプレビュー (REST API 2026-11-01-preview) と記載されています。実装時は最新のドキュメントと API バージョンを確認してください。

🛠️設定方法

前提条件 (Egress 制御)

  • Microsoft Foundry リソースと hosted agent
  • Foundry リソース上のガードレール (RAI ポリシー) とその完全な ARM リソース ID

REST API での Egress ルール設定例

bashEgress ポリシー (既定 Deny + Allow ルール) の構成
TOKEN=$(az account get-access-token --resource "https://management.azure.com" --query accessToken -o tsv)

curl -X PUT \
  "https://management.azure.com/subscriptions/<subscription-id>/resourceGroups/<resource-group>/providers/Microsoft.CognitiveServices/accounts/<account>/raiPolicies/<policy-name>?api-version=2026-09-01" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "properties": {
      "mode": "Blocking",
      "basePolicyName": "Microsoft.DefaultV2",
      "egressPolicy": {
        "mode": "Enforced",
        "defaultAction": "Deny",
        "rules": [
          {
            "name": "allow-contoso",
            "ruleType": "Fqdn",
            "match": { "host": "*.contoso.com" },
            "action": { "actionType": "Allow" }
          }
        ]
      }
    }
  }'

💎メリット

📈 ビジネス面

  • エージェントの外部接続先を組織ポリシーとして統制でき、データ流出リスクやシャドー接続を低減してコンプライアンス要件に対応しやすくなる
  • 社内ツールやサードパーティ API のライブデータをインジェストなしでエージェントのグラウンディングに活用でき、ナレッジ統合の開発コストを削減
  • Work IQ の Business Applications サポートにより、既存のビジネスアプリケーション資産からより多くの価値を引き出せる

⚙️ 技術面

  • Egress 強制はエージェントサンドボックスの外側で行われるため、エージェント自身のコードに依存しない信頼性の高い制御が可能
  • Audit モード + 既定 Deny で依存先を洗い出してから Enforce に移行する段階的な導入パスが用意されている
  • MCP ナレッジソースはインデックス型ソースと同じランキングパイプラインで統合され、単一の retrieve 応答で横断的な結果を得られる
  • Egress 判定が Application Insights とトレースに記録され、可観測性が確保されている

⚠️デメリット・制約事項

  • Egress 制御: Transform ルール、シークレット参照によるヘッダー値 (secretRef)、Azure Policy によるガバナンスはプレビュー。Azure Policy ガバナンスは hosted agents のみ対象で、現時点では Canada Central・Spain Central・Korea Central でのプレビュー提供
  • Egress 制御は prompt agents では Microsoft Copilot harness (プレビュー) 使用時のみサポートされ、その他の prompt agents やモデルデプロイには影響しない
  • Egress 制御は Azure Firewall などの既存のネットワーク制御を補完するものであり置き換えではない (ツーリングとしての提供。宛先エンドポイントのデータ取り扱いは利用者の責任)
  • RAI ポリシーへの書き込み権限はそれを使用するエージェントの挙動を変更できるため、エージェント更新権限と同等の信頼レベルで管理する必要がある
  • データプレーンの Azure Policy ガバナンス変更の反映には 30〜60 分かかる
  • MCP ナレッジソース: retrieval reasoning effort の minimal は非対応 (low / medium を使用)。alwaysQuerySource 非対応。外部ネットワーク呼び出しのため通常の検索より時間がかかる場合があり、maxRuntimeInSeconds の調整が推奨される。リモートソースのためバッキングインデックスがなく、citation URL は返されない
  • MCP サーバーの利用にはセキュリティリスク (攻撃、連鎖障害、人間の監督の喪失など) が伴うため、サーバーの検証・承認メカニズム・モニタリングの実装が推奨される
  • 利用可能リージョンは今回の発表には明記されていない (Foundry IQ は agentic retrieval 提供リージョンが前提)

💡ユースケース

📦 ユースケース 1: コーディングエージェントを承認済みレジストリに制限

シナリオパッケージインストールやソース取得を行う hosted agent を、承認済みのパッケージレジストリとソース管理 API のみに制限したい。

実装例既定アクション Deny の許可リストを作成し、必要なレジストリ・ダウンロードホスト・ソース管理 API を Allow ルールで追加。まず Audit モードで代表的なタスクを実行し、Egress 判定を確認して不足ホストを追加してから Enforce に切り替える。

効果パッケージマネージャーがリダイレクトや別のダウンロードホストを使うケースも Audit で検出でき、未承認宛先への通信を確実にブロックできる。

🚪 ユースケース 2: エンタープライズゲートウェイ経由への強制ルーティング

シナリオ特定の外部 API への通信を社内の承認済みゲートウェイ経由にしたい。

実装例Rewrite ルールでマッチしたホストをゲートウェイにリダイレクトする。非本番環境でテストしてから適用する。

効果エージェントのコードを変更せずに通信経路を統制できる。

🔌 ユースケース 3: 社内 API を MCP 経由でエージェントのナレッジに統合

シナリオFoundry IQ がネイティブ対応していない社内ツールやサードパーティ API の情報をエージェントの回答のグラウンディングに使いたい。

実装例社内システムの MCP サーバーを読み取り専用ナレッジソースとして登録し、ナレッジベースに追加。Azure AI Search インデックスや Web 検索ソースと組み合わせてクロスソース検索を構成する (テストには公開されている Microsoft Learn MCP サーバー https://learn.microsoft.com/api/mcp が利用可能)。

効果インジェストパイプラインを構築せずにライブデータを横断検索・統合ランキングでき、ナレッジ統合の実装工数を削減できる。

📝まとめ: Solutions Architect の視点

Microsoft Foundry のエンタープライズ対応が大きく前進したアップデートです。特にネットワーク Egress 制御の GA は、hosted agent を本番運用するうえでの必須要件だった「エージェントの外部通信の統制」をプラットフォームレベルで実現するもので、Solutions Architect はエージェント導入設計時に Audit モードでの依存先洗い出し → 既定 Deny の許可リスト → Enforce 移行という段階的な導入パスを標準プラクティスとして組み込むことを推奨します。
