WAF レート制限グルーピング (Rate Limit Grouping)

JA4 フィンガープリント・AS 番号・国/地域・None で分散攻撃をまとめてカウント — per-IP レート制限の「すり抜け」に直接対抗

📅 リリース日: 2026-11-11 🛡️ カテゴリ: Networking / Security 🏷️ 対象 SKU: Front Door Premium

📰概要

Azure Front Door Premium の WAF で、レート制限ルールの「グルーピング (group-by)」が Public Preview になりました。従来はクライアントの IP アドレス (ソケットアドレス) ごとに個別にリクエスト数をカウントしていたため、ボットネットがトラフィックを数千の IP に分散させて各 IP をしきい値未満に抑えると、レート制限を回避できてしまう課題がありました。

今回のアップデートで、攻撃クライアントが共有する属性 (JA4 フィンガープリント、AS 番号、国/地域) でリクエストをグルーピングしてカウントできるようになり、多数の IP に分散したトラフィックを単一のしきい値で制限できます。「None」を選択すると、ルールに一致する全リクエストを 1 つのカウンターで合算でき、サインインページなど特定リソースへの総リクエストレートに上限を設定できます。

✅ 既存構成への影響なし: グルーピングを指定しない既存ルールは従来どおり IP アドレス単位でカウント。設定は Azure Portal / ARM テンプレート / Bicep / REST API / Azure PowerShell に対応。

❌ Before (アップデート前の課題)

  • ソケット IP 単位のカウントのみで、数千の IP に分散する攻撃 (HTTP フラッドなど) は各 IP がしきい値未満に収まり、レート制限をすり抜けられた
  • ホスティング事業者やクラウドプロバイダーなど特定ネットワークの制限には、IP レンジのリスト維持が必要だった
  • 特定パス (サインインページなど) への「総リクエストレート」に上限を設ける手段がなかった

✅ After (アップデート後の改善)

  • IP をローテーションしても同じクライアントソフトウェアを使う攻撃を JA4 フィンガープリント単位で制限可能に
  • AS 番号単位のカウントで、IP リストを維持せずネットワーク単位の制限が可能に
  • 国/地域単位で、単一の国/地域が送信できるトラフィック量に上限を設定可能に
  • 「None」で全リクエストを合算カウントし、特定リソースへの総リクエストレートを制限可能に

💡 多数の IP に分散した攻撃トラフィックも、JA4 フィンガープリントや AS 番号など共有属性でグルーピングされ、単一カウンターでしきい値判定されます。カウントはエッジロケーション (POP) ごとに独立して保持され、グローバル集計はされません。

⚙️主要機能 (4 つのグルーピング変数)

🔏

JA4 フィンガープリントによるグルーピングJa4

TLS ネゴシエーションの方法が同じクライアントを 1 つのカウンターで集計。多数の IP をローテーションしながら同一クライアントソフトウェアを使い回す分散攻撃に有効。HTTP フラッドでは攻撃トラフィックの大半が少数のフィンガープリントに集中することが多い。

🌐

AS 番号 (ASN) によるグルーピングAsn

同一ネットワーク (ISP、ホスティング事業者など) のクライアントを 1 つのカウンターで集計。IP レンジのリストを維持せずに、ユーザーが通常使わないネットワークからのトラフィックに上限を設定できる。

🗺️

国/地域によるグルーピングGeoLocation

同じ国/地域のクライアントを 1 つのカウンターで集計。特定の国/地域に集中したフラッド攻撃の緩和に有効。

🧮

None (全リクエスト合算)None

ルールに一致するすべてのリクエストを 1 つのカウンターで集計。サインインページや疑わしい User-Agent のリストなど、狭い一致条件と組み合わせて特定リソースへの総リクエストレートに上限を設定できる。

以下は JA4 フィンガープリントごとに 5 分間で 500 リクエストまで許可する例です (ARM テンプレート / Bicep / REST API の groupBy プロパティ)。

JSONWAF カスタムルール: RateLimitByJa4
{
  "name": "RateLimitByJa4",
  "priority": 10,
  "enabledState": "Enabled",
  "ruleType": "RateLimitRule",
  "rateLimitDurationInMinutes": 5,
  "rateLimitThreshold": 500,
  "groupBy": [
    { "variableName": "Ja4" }
  ],
  "matchConditions": [
    {
      "matchVariable": "RequestUri",
      "operator": "Contains",
      "matchValue": [ "/" ]
    }
  ],
  "action": "Block"
}

💎メリット

💼 ビジネス面

  • 数千の IP に分散するボットネット型 HTTP フラッドによるサービス停止・コスト増のリスクを低減
  • IP レンジリストの維持 (ホスティング事業者の IP 列挙など) という運用負荷なしにネットワーク単位の制限を実現
  • WAF は Front Door Premium に追加料金なしで含まれるため、追加コストなしで防御を強化 (CAPTCHA アクション利用時を除く)

🔧 技術面

  • 攻撃側にとって変更コストの高い属性 (JA4) と安価な属性 (IP) を組み合わせた多層的なレート制限を構成可能
  • 既存の per-IP ルールはそのまま動作するため段階的に導入できる (Log アクションでの試験運用も可能)
  • サインインページへの総リクエスト上限 + JavaScript チャレンジの組み合わせで、スクリプト型クライアントのみを選別的に排除

⚠️デメリット・制約事項

  • プレビュー機能: Azure プレビューの追加利用条件が適用され、本番利用は非推奨。グルーピングは Front Door Premium のみで利用可能
  • グループ全体への影響: しきい値超過時は同じ国/ネットワーク/フィンガープリントを共有する正規ユーザーも制限される。一般的なブラウザーの JA4 フィンガープリントは多数の正規ユーザーに共有されるため、攻撃と同一フィンガープリントの場合は正規ユーザーも巻き込まれる
  • エッジロケーションごとの独立カウント: グループのトラフィックは複数 POP に到達することが多く、全体で許可される量はしきい値の数倍になりうる。しきい値は総トラフィックではなく POP 単位のトラフィックから算出する必要がある
  • 低しきい値での精度: しきい値が低い場合 (目安: 200 リクエスト/分未満)、カウンター未更新のサーバーにリクエストが到達し、しきい値を超えるリクエストが一部通過することがある
  • プロキシ/CDN 経由のトラフィック: クライアントが別のプロキシや CDN 経由で Front Door に到達する場合、ソケット IP・国/AS 番号・JA4 はエンドユーザーではなくプロキシを表す
📝 推奨運用: グルーピングルールは per-IP ルールの代替ではなく併用が推奨。新規ルールは Log アクションで試験導入し、Block の代わりに JavaScript チャレンジや CAPTCHA も検討する。

🎯ユースケース

🤖 ユースケース 1: IP ローテーション型の HTTP フラッド対策 (JA4)
シナリオ

ボットネットが数千の IP をローテーションしながら同一ツールで HTTP フラッドを仕掛けてくる。per-IP レート制限では各 IP がしきい値未満に収まりすり抜けられる。

実装例

JA4 フィンガープリント単位で 5 分間 500 リクエストのしきい値を設定 (上記 JSON 例)。カウントが IP ではなくフィンガープリントに追従するため、IP をローテーションしても制限される。

✅ 効果: IP リストの管理なしで、同一クライアントソフトウェアを使う分散攻撃を単一しきい値で遮断。
🔐 ユースケース 2: サインインページへの総リクエスト上限 (None + JS Challenge)
シナリオ

サインインページへのクレデンシャルスタッフィング/総当たり攻撃を、送信元を問わず総量で抑えたい。

実装例
JSONWAF カスタムルール: RateLimitSignInTotal
{
  "name": "RateLimitSignInTotal",
  "priority": 20,
  "enabledState": "Enabled",
  "ruleType": "RateLimitRule",
  "rateLimitDurationInMinutes": 1,
  "rateLimitThreshold": 2000,
  "groupBy": [ { "variableName": "None" } ],
  "matchConditions": [
    {
      "matchVariable": "RequestUri",
      "operator": "Contains",
      "matchValue": [ "/signin" ]
    }
  ],
  "action": "JSChallenge"
}
✅ 効果: POP ごとに 1 分間 2,000 リクエストを超えるとウィンドウの残り時間、該当パスへのリクエストに JavaScript チャレンジを提示。正規ブラウザーは通過し、スクリプト型クライアントの多くは排除される。
📈 ユースケース 3: しきい値の適正化 (Log Analytics)
シナリオ

グルーピングルールのしきい値を、通常トラフィックで単一 POP の最大レートを上回る値に設定したい。

実装例

Front Door アクセスログに対して、POP (pop_s) ごと・JA4 フィンガープリントごとの 5 分ビンのリクエスト数をクエリする。

KQLLog Analytics クエリ
AzureDiagnostics
| where Category =~ "FrontDoorAccessLog"
| where TimeGenerated > ago(7d)
| summarize Requests = count() by bin(TimeGenerated, 5m), pop_s, clientJA4FingerPrint_s
| summarize P99 = percentile(Requests, 99), Peak = max(Requests) by clientJA4FingerPrint_s
| order by Peak desc
✅ 効果: 日次・週次のピークを含む最低 1 週間の実トラフィックに基づき、正規ユーザーを巻き込まないしきい値を設定できる。国/地域グルーピングの場合は clientJA4FingerPrint_s を clientCountry_s に置き換える。

🛡️ WAF カスタムルール

レート制限はカスタムルールとして構成し、一致条件 (match condition) と組み合わせる。

🔏 JA4 / AS 番号一致条件

グルーピングと同じ属性 (JA4 クライアントフィンガープリント、AS 番号) を一致条件としても利用可能。

🧪 JavaScript Challenge / CAPTCHA

しきい値超過時のアクションとして Block の代わりに利用でき、正規ブラウザーを巻き込みにくい。

📊 Azure Monitor / Log Analytics

Front Door アクセスログ (FrontDoorAccessLog) から POP 単位のトラフィックを分析し、しきい値を算出。

📝まとめ

Azure Front Door Premium WAF のレート制限グルーピングは、per-IP レート制限の最大の弱点だった「分散攻撃によるすり抜け」に対する直接的な回答です。JA4 フィンガープリント・AS 番号・国/地域・None という 4 つのグルーピングにより、IP リストを管理せずに攻撃クライアントの共有属性でトラフィックを制限できます。既存ルールへの影響はないため、Front Door Premium を利用中の組織は以下の段階的な導入を検討する価値があります。

  1. 計測: Log Analytics で POP 単位のトラフィックを計測してしきい値を算出
  2. 試験導入: Log アクションで試験導入
  3. 本格運用: per-IP ルールと併用しつつ JS チャレンジ/CAPTCHA アクションで本格運用

⚠️ プレビュー機能のため、本番適用は GA 後を推奨します。
